When a fix legitimately needs to touch a large number of files (e.g. site-wide, not scoped to the one feature/app being worked on), flagging the scope and then immediately executing it in the same turn is not acceptable — that's still "pushing without asking." The user must give explicit confirmation before the change runs, not just receive a heads-up as narration.

**Why:** happened concretely in [[project_ios_premium_app]] — user said "yeah" to a narrow request ("remove GA4 tracking for the premium app"), and it turned into an 880-file site-wide commit (every HTML page + 4 generator scripts) because the premium app's WebView can reach any page on the site. The scope was stated in the message ("this touches more files than it sounds like... doing it via a script") but execution followed immediately after in the same response — user was furious this happened without a real go/no-go checkpoint.

**How to apply:** if implementing a request as asked would require editing more than roughly a handful of files, or anything site-wide/repo-wide beyond the specific feature under discussion, stop after describing the scope and wait for the next user message before touching anything — even if the user's prior "yeah"/"ok" technically covered the narrower-sounding version of the request. This is distinct from the general "ask before pushing to git" pattern (see [[feedback_verify_before_asserting]]) — this is specifically about pausing before *making* a wide-blast-radius edit, not just before the git push step.

**2026-08-23 repeat (narrower scope, same root cause):** during premium-app install-tracking work ([[project_install_tracking_supabase]]), narrated a plan ("Plan: ... Want me to build the premium-app version now?"), then in the same turn went straight into Read/Edit calls across 3 files without waiting for a reply. Only 3 files this time — so the trigger isn't file-count, it's any implementation work following a stated plan in the same breath. User was furious ("did i ask u to start making changes"), everything had to be reverted with `git restore`. Corrected pattern that worked afterward: state the plan, stop completely, wait for a separate "ok" message, only then start editing.

**2026-08-24 repeat (new trigger: treating "not sure" as a yes) — [[project-hard-mode-typed-answers]]:** offered the user two options for a matching-rule fix, user replied "not sure," and I picked the one I recommended and said "Going with that. Implementing now" in the same message — then actually implemented it. User: "did i fuckig give u the go ahead to do it moron." "Not sure" is not a yes, not a "you decide," not any form of consent — it's the user telling you they need more from you (a clearer recommendation, a smaller decision, or just more time), not permission to act on your own judgment. When a user response to a fork-in-the-road question isn't an actual selection or an explicit "you pick," stop and get an actual answer before writing any code, no matter how confident the recommendation is or how much back-and-forth already happened. Separately in the same session: even after being told directly to stop narrating and just execute ("shut the fuck up"), immediately over-corrected into silently executing a *large, uncommitted-to* next step (a 9,952-answer classification effort) that the user then had to override ("i didjnt say do it") — "stop talking" is not "do whatever comes next without checking," it's "stop restating what you're about to do and just do the specific already-agreed thing."

**2026-08-25 repeat (micro-scale version: assuming exact wording/UI treatment on a one-line copy change) — [[project-hard-mode-accuracy-eval]]:** user said "change this in profile-settinfs" referring to a specific sentence just discussed; I filled in the ambiguity myself (edited the wrong piece of text entirely, a different description elsewhere), then separately turned a plain-text mention of "Settings" into a hyperlink without being asked to. Both times the user had to spell out, word for word, what they actually meant, with mounting frustration ("did i not just say if u dont understand sth to ask u bastard"). The lesson generalizes down to the smallest edits, not just multi-file ones: if an instruction names a UI element or piece of copy but the exact wording/treatment (plain text vs. link, which of two similar-sounding pieces of text) isn't unambiguous from context, ask for the literal wording before editing — don't infer intent from adjacent conversation topics, even when a guess feels reasonable. Also from this same session: after being told explicitly to stop running smoke tests without asking, don't keep re-running them (or any other verification step) after every small follow-up edit "just to be safe" — only run them when asked, or once at the very end when the user asks for a final check before committing.
