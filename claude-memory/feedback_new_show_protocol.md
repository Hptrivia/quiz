When the user says "add a new show" (or similar), follow this exact sequence. It was NOT guessed from reading the scripts — it was verified by diffing the actual last real batch (commit `6a46fb27`, 2026-08-02, added: hawk, homeland, leftovers, oc, orange, oz, shield, veep) against what each script claims to do, so it reflects what's really used, not just what's theoretically possible.

**Step 1 — question file. User does this, not me.** They paste/write `data/<name>.txt` themselves — a JSON array of `{question, options:[4], answer, difficulty}`. My only job here is to review/fix it (e.g. [[project-filler-question-reordering]]-style cleanup), never to author questions myself unless asked.

**Step 2 — `data/themes.json` entry. I write this.** For each new show, propose the category first (must be exactly one of: `TV, Movies, Anime, Sitcoms, Games, Sports, General, Education, Books, Countries`) and get the user's confirmation before writing anything. Then append a new object: `slug, title, category, description, image:"", questionFile, seoIntro, seoDetail, fanQuestions` (bool, usually `true`). Write `description`/`seoIntro`/`seoDetail` matching the tone/depth of existing entries — named characters, plot beats, why the quiz "works" as a theme. **Append-only — never edit an existing theme's entry.** Note: `scripts/add-seo-details.js` has a `contentMap` upsert pattern that looks like it's meant for this, but it's dead — last touched April 2026, not used in the real Aug 2 batch. `themes.json` gets edited directly. Ignore that script.

**Step 3 — `node scripts/build-site.js`.** Runs `generate-theme-pages.js` (builds `themes/<slug>.html`, rewrites `sitemap.xml` — lastmod-preservation already built in here, safe) → `generate-category-pages.js` (rebuilds all `categories/*.html`, but only categories that got a new entry actually change) → `generate-recent.js` (rebuilds `data/recent.json`, dated by the questionFile's first git-commit date — so ideally commit the `.txt` before running this, else it falls back to file mtime).

**CORRECTED 2026-08-11 — use `ONLY_SLUGS` every time, don't run `node scripts/build-site.js` bare.** Earlier version of this memory said the ~240-file theme-page churn from Step 3 was harmless and expected — that was wrong, and the user called it out sharply. `generate-theme-pages.js` picks a random FAQ sample (`Math.random()`) on every run, so a bare run rewrites every existing theme page's HTML, not just new ones. The script already has the fix built in: set `ONLY_SLUGS=slug1,slug2,...` (comma-separated, the new shows' slugs) as an env var before running `generate-theme-pages.js` (or `build-site.js`, which just calls it) — this scopes which `themes/<slug>.html` files actually get rewritten to disk, so unrelated shows are never touched. **Always use this for new-show batches.** If a bare run already happened by mistake, recovery is: `git status --porcelain themes/` to list modified (not `??`) files, exclude the new shows' slugs, `git checkout --` the rest.
**`sitemap.xml` is a separate, unfixable-by-ONLY_SLUGS case — leave it alone unless asked.** The script's own comment explains why: sitemap URL collection always walks every theme regardless of `ONLY_SLUGS`, otherwise it'd drop every URL not in the scoped set. So `sitemap.xml` gets fully rebuilt in canonical theme-order every run, and if the on-disk file has any URLs out of that canonical order (e.g. wordle/wordsearch URLs appended by their own separate generator scripts rather than grouped with the theme), the rebuild moves them — a large-looking diff that is still safe (verified: no URLs lost, `lastmod` values preserved, pure reordering). Don't proactively "fix" this reordering by hand-editing the generator; it's pre-existing structural behavior unrelated to adding new shows. Just don't run the sitemap-writing step until the very end of a batch (after all shows' wordle/wordsearch pages are also generated) so it only needs to be regenerated once, not once per script invocation.

**Step 4 — `data/wordle_words.txt` entry. I write this.** Key = exact theme **Title** (not slug). 12 words, ALL CAPS. **Strict 4–7 letters each** — not shorter, not longer, so the board doesn't get too easy or too complicated. Then `node scripts/generate-wordle-pages.js` builds `wordle/<slug>.html` and updates the sitemap. **Fixed 2026-08-07**: this script used to blindly re-date every existing `/wordle/` sitemap URL to "today" on every run (strip-all-and-readd pattern) — now it preserves existing `<lastmod>` values the same way step 3's script does, only new URLs get today's date.

**Step 5 — `data/wordsearch_words.json` entry. I write this.** Key = exact theme **Title**. 24 words total: ~12 character/proper-noun names first, then the *exact same* 12 words from that show's `wordle_words.txt` entry appended after (confirmed pattern from real data — wordsearch list = names + wordle list, verbatim). Word length **3–9 letters** so it fits the grid. Then `node scripts/generate-wordsearch-pages.js` builds `wordsearch/<slug>.html` and updates the sitemap. **Also fixed 2026-08-07** with the same lastmod-preservation logic as step 4.

**Word-selection rules for steps 4/5 (learned the hard way on 2026-08-07, batch-testing 7 shows — get these right the FIRST time, don't repeat the correction cycle):**
- **Prefer theme/plot words over character names in the wordle list.** Names are the fallback, not the default — reach for objects, places, events, terms specific to the show first. Only use a name if there genuinely isn't a good themed word left (most shows have enough vocabulary to hit all 12 with zero names — check the real Homeland/Oz/Silo data before assuming you need names).
- **CORRECTED 2026-08-21 — popularity/recognizability overrides the theme-word-over-name preference above.** Called out sharply during a 16-show batch (Archer/BoJack/X-Men/Bond/Furious/Horses/India/Indiana/Matrix/Pirates/Swift/Terminator/Transformers/Wick/China/Russia). Don't default to obscure deep-cut trivia (a random prop, a one-scene location, a minor plot device) just to avoid a name. If the single most popular/iconic thing about a show is a character name or an iconic named object (Optimus Prime, Megatron, Daisy the puppy, the High Table), that belongs in the wordle list itself, not exiled to the wordsearch-only names section. Real rule: **lead with whatever's most recognizable to a fan of the show, whether that's a name or a plot word — don't bury famous elements in wordsearch just to keep wordle "name-free."** Weak/overly-subtle single-scene details (e.g. "which finger does he cut off," "what currency do they use") get cut in favor of more iconic terms even if it means more character names in the 12.
- **If a name is used in wordle, never let it lead the list** — put it in the middle, not first or last. (This positioning rule still applies even under the corrected popularity-first guidance above.)
- **Every word must be something that actually happens/exists IN the show** — a real prop, place, event, or in-universe term the audience would recognize from watching. Read the actual question file (or draw on real canon knowledge of the show beyond just that file — not restricted to only the literal Q&A text) and ground every single word in a specific fact. Do NOT default to generic genre vocabulary that could apply to any similar show (e.g. "TRAP/MIXTAPE/HUSTLE" for any rap-adjacent show) — that was called out as lazy and wrong.
- **NEVER use real-world actor/actress/author/director surnames as words.** They are never spoken or seen inside the show's fictional world — Stanfield, Ferguson, Kunis, Rhys, Russell, Taylor (Eliza), Morgan (Kass) were all real mistakes caught this session. Only in-universe character names and terms belong in either list. This applies even though actor names are the traditional "which actress plays X" trivia answer pattern in the question file — that's a valid quiz *question*, not a valid word-list *entry*.
- **Don't split one real entity across two slots** — e.g. "Todd Rundgren" (one musician) became `TODD` + `RUNDGREN`, wasting two of twelve slots on one thing. Same failure mode as the actor-name issue: check that every slot represents something distinct.
- **Wordsearch names should be a natural MIX of first names and surnames**, not uniformly one or the other — mirror the real data (Homeland: `CARRIE, BRODY, SAUL, QUINN, MATHISON, BERENSON, ESTES, NAZIR, DANA, JESSICA, YEVGENY, HAQQANI` mixes both). An all-surname list (`UNDERWOOD, STAMPER, RUSSO...`) reads as monotonous and less recognizable than leading with the character's actual commonly-used name (`FRANK, CLAIRE, STAMPER...`).
- **Present category + both word lists to the user for confirmation, one show at a time, before writing anything to the data files.** Do the `themes.json` entry and everything else first if doing a batch, but the word lists are the one step that always needs a stop-and-check per show — don't write them speculatively and ask forgiveness after.
- **Present word-list confirmations as plain chat text, never via the AskUserQuestion grid tool.** Confirmed 2026-08-11: user wants to just reply in chat like normal, not pick from a UI grid. This applies to the word-list check specifically (and probably other back-and-forth confirmations in this workflow) — ask in prose, wait for a normal reply.
- **CORRECTED 2026-08-28 — wordle is the flagship product, wordsearch is not. The MOST common/recognizable things about a theme belong in wordle; save the deeper-cut/interesting-but-secondary stuff for wordsearch.** Called out sharply (Belgium batch): put TINTIN and POIROT in wordle — real Belgian cultural exports, not wrong facts, just not what a casual player's mind jumps to first for "Belgium." The wordsearch names section is exactly where second-tier-but-still-recognizable proper nouns belong (that's where Tintin/Poirot-style picks ended up instead) — wordle's 12 slots should read as "the obvious answers a random person would blurt out," not "the most interesting facts I could dig up." This sharpens (doesn't replace) the 2026-08-21 popularity-over-theme-word correction above: recognizability was already the right axis, this just raises the bar for what counts as recognizable enough for wordle specifically.
- **CORRECTED 2026-08-28 — avoid 4-letter words in wordle.** Even though 4–7 is the stated range, the user dislikes 4-letter wordle words specifically (e.g. NATO, BEER) — treat the effective floor as 5 letters and only drop to 4 if there's truly no 5+ letter option that fits.
- **CORRECTED 2026-08-28 — cap wordle names at 3-4 max out of the 12, even under the recognizability-first rule above.** Confirmed working well on a 15-show batch (user: "the wordle is so much better now... make sure whatever u did to get the good words is remembered"), but flagged that How to Get Away with Murder's list had 7 character names out of 12 — too many, even though each individual name was arguably the most "recognizable" choice for its slot. The fix: after drafting a wordle list, count the names — if it's above 3-4, swap the weaker/less-essential names back out for plot/setting/object/concept words (a "core show mechanic" term, an iconic prop, the setting itself) even if those are individually a notch less recognizable than one more character name would be. This means for very character-driven shows (ensemble legal/crime dramas etc.) some genuinely well-known characters will NOT make the wordle 12 and instead belong in the wordsearch names section instead — that's fine, wordsearch is exactly where the overflow of "recognizable but not top-4" names belongs. The 2026-08-21 popularity-over-theme-word rule still governs WHICH names make the cut (most iconic first), just capped in count now.
- **What "good" wordle lists looked like on the 2026-08-28 batch (Belgium/France/South Korea/Spain/Cobra Kai/White Collar/Loki/Call the Midwife), for pattern-matching next time:** lead with the single most obvious, googleable, "first thing anyone would say" associations (capital city, signature food, the title word itself, the lead character's name) — not clever deep-cuts. Every word grounded in a specific, verifiable fact (real geography/history for countries; real plot/character detail — checked against the actual question file plus genuine canon knowledge — for shows). 5-7 letters preferred, 4-letter only as a last resort, nothing over 7. Names capped at 3-4 (see above), never leading or trailing the list. The "second-tier but still genuinely recognizable" material (extra characters, deeper lore terms, historical figures, landmarks) is exactly what the wordsearch names section is for, not overflow to cut entirely.
- **For every wordle word, show a one-line gloss of what it means in relation to the show** right next to the word when presenting the list for approval (e.g. `ITIS — name of Grandad's soul food restaurant`). Requested 2026-08-11 so the user can sanity-check relevance without cross-referencing the question file themselves.

**Step 6 — `node scripts/validate-themes.js`. Optional, my own sanity check.** The user isn't sure this is actually part of their workflow — treat it as something I run myself to catch typos before/after, not a step to formally report on. Known false positive: it flags every `xxxeps1.txt` episode file as "unused" due to a bug (it checks filenames for the substring `"episode"`, but the real naming convention is `eps1`) — ignore those specific warnings, they don't mean anything.

**Step 7 — bump `index.html` category counts. I do this by hand.** No script does this. The homepage has hardcoded `<p>N theme(s)</p>` per category card (e.g. `<h3>TV</h3><p>93 theme(s)</p>`) — after adding shows to a category, increment that number to match the new total. Easy to forget since nothing errors if you skip it — the homepage just quietly shows a stale count.

**Step 8 — `node scripts/smoke-test.js`. Final QA.** Puppeteer-based, plays through every game mode headless and fails on JS errors or a mode never reaching its end state. Run after everything above, as the last check that nothing broke.

**Step 9 — `node scripts/hardmode-accuracy-eval.js`. Also run after adding a new show, added 2026-08-25.** It scans EVERY `data/*.txt` file each time, so the new show's answers are automatically included with zero extra wiring -- nothing to update per-show. It's informational (prints a shape breakdown + pass-rate table, no exit-code gate), not a hard blocker -- but a new show can introduce answer shapes the matcher hasn't seen before (e.g. a title-shaped answer with unusual punctuation, or an all-caps acronym), so worth a skim for any bucket rate that drops noticeably versus the last known baseline (93.2% overall as of 2026-08-25 -- see [[project-hard-mode-accuracy-eval]]). Only meaningful once Hard Mode itself is actually merged/live; skip this step until then.

**Step 10 — add an announcement popup entry for the new show(s). Always the last step, added 2026-08-26.** Append an entry to `APP_ANNOUNCEMENTS` in `assets/announcements.js` (the reusable one-time popup, built during the Category Blitz project — see [[project-napt-game-mode]]) announcing the new theme(s), e.g. `"🆕 New: [Show Name] added — check it out!"` with a `cta` linking to `themes/<slug>.html` (or the category page if it's a multi-show batch). Seen-tracking there is by a hash of the entry's exact text, not a manual id — no extra bookkeeping needed, just write the line. Explicitly requested by the user as a standing step, not a one-off.

**Dead — skip entirely:** `scripts/generate-wordle-hints.js` / `data/wordle_hints.json`. The script exists but its output file doesn't exist anywhere in the repo, and nothing in the live wordle game reads it. Never actually wired in — don't bother running it.

**Optional — skip unless the user explicitly asks:** `data/episode_themes.json` (episode mode, only if an `xxxeps1.txt` file exists for that show), `data/normal_pack_links.json` / `episode_pack_links.json` (Ko-fi printable-pack purchase links), `data/affiliate_links.json` (real Amazon affiliate URLs — I cannot fabricate these; only add if the user hands me actual links).

**`data/new_themes.json` (drives `categories/newly-added.html` via a "Newly Added" filter in `assets/app.js`) — leave this alone unless explicitly asked, and even then check first.** Briefly corrected 2026-08-21 to "always auto-update this every batch," then reverted the same session: `categories/newly-added.html` is orphaned from the live UI — it's in the sitemap and has intro copy in `app.js`, but nothing on the homepage or any nav links to it, so keeping the slug list current doesn't actually surface anything to real users. Don't touch it as part of the standard batch; only update it if the user explicitly asks AND confirms that page is still meant to be in play. This is a different file from `data/recent.json` (the "Recently Added" page, `recent.html`, linked from the homepage nav) — that one IS still live and DOES get auto-regenerated every batch via `generate-recent.js` in step 3, no confusion between the two.

**Hard rule across every step, per explicit user instruction:** Adding a new show must never modify an existing show's `themes.json` entry, generated page, word list, or sitemap `<lastmod>` date as a side effect. Every step is append-only / new-URLs-only.
